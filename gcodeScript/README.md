# docx2gcode — текст із DOCX-таблиці у G-code для письмового плотера

Читає заповнену таблицю (будь-який `.docx`), розкладає текст по клітинках
порожнього бланка (`1 лист.docx`) і генерує G-code, яким плотер пише на
надрукованому бланку.

Працює на **macOS** і **Windows** (а також на Linux). Потрібен Python 3.10+.

---

## 1. Встановлення

```bash
python3 -m pip install fonttools
```

Це єдина залежність. DOCX читається штатними засобами Python.

На Windows замість `python3` зазвичай `python`.

---

## 2. Шрифт — прочитайте перед першим запуском

Скрипт бере обриси літер із реального файлу шрифта. Типово це **Segoe Script**
— рукописний шрифт, що лежить файлом `Segoe_Script.ttf` **у самій теці
проєкту**.

Встановлювати його в систему не потрібно: скрипт шукає шрифти не лише в
системних теках, а й поруч із собою. Тому будь-який свій `.ttf` або `.otf`
достатньо покласти в теку проєкту (або в підтеку `fonts/` — обхід
рекурсивний), і він знайдеться за назвою родини. Це працює й на Windows, і на
Linux, і шрифт подорожує разом із проєктом.

У `--font` пишеться **назва родини, а не імʼя файлу**. Вони часто не
збігаються, тому точну назву беріть із `--list-fonts`:

```bash
python3 docx2gcode.py --list-fonts segoe
```

```
Segoe Script    /Users/…/gcodeScript/Segoe_Script.ttf
```

Для одноштрихового письма монолінійні шрифти підходять найкраще: осьова лінія
з них виходить чиста. Контрастні шрифти з чергуванням товстих і тонких штрихів
дають лінію, що гуляє на переходах товщини.

**Перший запуск усе одно робіть із `--check-font`** — це швидка перевірка,
що всі символи документа шрифт справді вміє намалювати:

```bash
python3 docx2gcode.py "таблиця.docx" --check-font
```

На типовому шрифті звіт має виглядати так:

```
Шрифт: Segoe_Script.ttf
Символів у документі: 106   покрито: 106   відсутні: 0   порожні: 0

Усі символи документа підтримуються шрифтом.
```

Якщо ж якихось символів бракує (типова проблема декоративних шрифтів —
немає кирилиці), звіт перелічить їх поштучно:

```
Символів у документі: 106   покрито: 71   відсутні: 35   порожні: 0

Немає у шрифті:
  U+0416  «Ж»  CYRILLIC CAPITAL LETTER ZHE
  ...
```

Тоді варіанти такі:

* покласти в теку проєкту інший шрифт із кирилицею і вказати його назву:
  `--font "Назва родини"`
* вказати файл напряму абсолютним шляхом:
  `--font /шлях/до/шрифта.otf`
* дописати відсутні символи запасним шрифтом:
  `--fallback-font "Segoe Script"`

Подивитися, що взагалі доступно:

```bash
python3 docx2gcode.py --list-fonts segoe
python3 docx2gcode.py --list-fonts          # усі шрифти
```

Приймаються `.ttf`, `.otf`, `.ttc` і `.otc`. Останні два — колекції з кількох
накреслень в одному файлі; потрібне вибирається через `--font-index`. Веб-формати
`.woff`/`.woff2` і Type 1 не приймаються — їх треба конвертувати в `.ttf`/`.otf`.

> Відносні шляхи в `--font` ненадійні: «Створити G-code.app» запускається з
> робочою текою `/`, тому `./Segoe_Script.ttf` спрацює з термінала й зламається при
> перетягуванні файлу на іконку. Використовуйте назву родини або абсолютний шлях.

## 3. Швидкий старт

```bash
python3 docx2gcode.py "таблиця.docx"
```

Імʼя файлу-джерела не має значення — `таблиця.docx` тут і далі просто приклад.
Отримаєте в `gcodeOutput` по файлу на аркуш; імена складаються з назви джерела
й номера аркуша: `таблиця_p01.gcode`, `таблиця_p02.gcode`, … Текст пишеться одноштриховим режимом `centerline` — це типова
поведінка, прапорець для неї не потрібен.

Ні бланк, ні теку виводу вказувати не обовʼязково:

* бланк — скрипт сам візьме `1 лист.docx` поруч із джерелом (а якщо там немає —
  поруч зі самим скриптом); `-t` потрібен лише для іншого бланка;
* вивід — типово це тека `gcodeOutput` **поруч із текою проєкту**, щоб
  згенеровані файли не змішувалися з джерелами; `-o` перекриває це.

Разом із G-code туди ж кладеться `таблиця_preview.svg` — прев'ю 1:1
для звірки з бланком. Оптимізація холостих ходів теж увімкнена типово.
Вимикають їх `--no-preview` і `--no-optimize`.

### Без термінала: перетягування на іконку

Основний спосіб для тих, хто не працює з командним рядком. Обгортки лежать
**поруч із текою проєкту**, а не в ній — разом із текою `gcodeOutput`:

```
Documents/
├── gcodeScript/          ← сам скрипт і його файли
├── gcodeOutput/          ← готовий G-code
├── Створити G-code.app   ← macOS
└── Створити G-code.bat   ← Windows
```

Завдяки цьому теку проєкту відкривати не потрібно взагалі. Зібрати або
перезібрати обгортки:

```bash
./make_droplet.sh            # поруч із текою проєкту (типово)
./make_droplet.sh ~/Desktop  # або деінде, наприклад на робочому столі
```

Далі кидайте `.docx` на іконку **«Створити G-code»**. Файл при цьому
**залишається там, де лежав** — програма лише читає його, а результат кладе в
теку `gcodeOutput` поруч із текою проєкту. Наприкінці показує вікно зі звітом і
кнопкою «Показати теку».

Іконку можна ще й перетягнути в Dock і кидати файли просто на неї. Крім того,
програма зʼявляється в контекстному меню Finder у розділі **«Відкрити у
програмі»**, тож `.docx` можна обробити навіть без перетягування, правим кліком.
Типовою програмою для `.docx` вона при цьому не стає.

Шлях до теки проєкту вшивається в програму під час збірки, тому `.app` може
лежати будь-де. **Якщо теку проєкту перенесли або перейменували — запустіть
`make_droplet.sh` знову**, інакше програма покаже вікно з попередженням, що не
бачить `docx2gcode.py`.

Ще дві умови: у системі потрібен Python із `fonttools` (обгортка сама перебирає
типові місця, включно з `.venv` у теці проєкту), а при першому запуску macOS
може заблокувати її як «програму з невідомого джерела» — тоді відкрийте один
раз через **правий клік → Відкрити**. Якщо чогось бракує, обгортка показує вікно
з причиною, а не падає молча.

#### Дозволи macOS

Проєкт лежить у `Documents`, а це захищена тека, тому при першому перетягуванні
macOS запитає дозвіл на доступ до неї — натисніть **«Дозволити»**. Якщо `.docx`
лежить на робочому столі або в завантаженнях, буде окремий запит і на них: це
три різні категорії дозволів. Один раз погодилися — далі працює молча.

Якщо ж замість запиту зʼявляється вікно з `Operation not permitted`, дозвіл
колись відхилили. Скинути й отримати запит знову:

```bash
tccutil reset SystemPolicyDocumentsFolder com.docx2gcode.droplet
```

Або видайте дозвіл вручну: **Системні налаштування → Приватність і безпека →
Файли та теки**, знайдіть «Створити G-code» і ввімкніть потрібні теки.

> **Важливо для правок збірки.** `osacompile` підписує програму сам, а будь-яка
> зміна `Info.plist` після цього ламає підпис. Зі зламаним підписом macOS не
> може встановити особу програми й відмовляє в доступі до файлів **навіть без
> запиту** — саме так і виглядає `Operation not permitted`. Тому в
> `make_droplet.sh` `codesign` стоїть останнім кроком, уже після всіх правок
> `Info.plist`, і результат перевіряється `codesign --verify`. Стабільний
> `CFBundleIdentifier` теж не декоративний: без нього дозвіл нема за що
> зачепити, і після кожної перезбірки його доводилося б давати заново.

На Windows те саме робить **«Створити G-code.bat»**: киньте `.docx` на цей файл,
і він відкриє консоль зі звітом. Він працює у двох положеннях — поруч із текою
`gcodeScript` або всередині неї — і потрібне знаходить сам. Для нетипового
розташування впишіть шлях до теки проєкту у змінну `PROJECT` на початку файлу.

### Без термінала: покласти файл у теку

Альтернатива: тека сама стежить за собою, і кинутий у неї `.docx` обробляється
без жодних іконок. Вмикається один раз:

```bash
./install_watcher.sh          # увімкнути
./install_watcher.sh --off    # вимкнути
```

Скрипт ставить `launchd`-агент, який стежить за текою й запускає
`watch_folder.sh` на кожну зміну. Той обробляє лише нові `.docx`, пропускаючи
бланк `1 лист.docx` і тимчасові файли Word (`~$…`). Той самий файл двічі не
обробляється: у `gcodeOutput/.processed` запам'ятовуються імʼя, розмір і час
зміни. Відредагували й кинули знову — обробиться. Щоб перегенерувати той самий
файл без змін, очистіть `.processed`.

У цього способу два недоліки, через які він тут другий:

* **файл переміщується в теку проєкту** — перетягування на теку в Finder це
  завжди «перемістити», а не «обробити на місці»;
* **тека проєкту мусить бути поза `Documents`, `Desktop` і `Downloads`.** macOS
  не дає фоновим агентам читати ці три теки, причому молча: агент запускається,
  але отримує `Operation not permitted`. `install_watcher.sh` це перевіряє й
  відмовляється встановлюватися, щоб не залишити конфігурацію, яка тихо не
  працює. Щоб спосіб заробив, перенесіть проєкт, наприклад у `~/gcodeScript`.

Журнал помилок агента: `/tmp/com.docx2gcode.watch.log`.

## 4. Два режими письма

| Режим | Що робить перо | Кому підходить |
|---|---|---|
| `--mode centerline` *(типово)* | веде **один штрих** по осі літери | справжнє рукописне письмо; удвічі коротший шлях, на чверть менше часу |
| `--mode outline` | обводить контур кожної літери | тонке перо 0.3–0.5 мм; точно відтворює насиченість шрифта |

`centerline` (типово) розраховує осьову лінію (скелет) літери й веде перо по
ній — виглядає як написане від руки. На тому самому документі: 21.0 м письма
проти 41.7 м, 48 хв проти 66 хв.

Виграш у часі менший, ніж у довжині письма, бо скелет розпадається на більше
окремих штрихів (8320 контурів проти 4421), а на кожен штрих перо піднімається
й опускається. Тому в `centerline` хід по Z майже вдвічі довший — 41.6 м проти
22.1 м.

`outline` малює контур, тому лінія літери виходить подвійною — пером
0.4–0.5 мм вони зливаються в суцільний штрих. Тонким пером літери вийдуть
порожнистими всередині.

Якщо не впевнені — зробіть обидва прев'ю і подивіться:

```bash
python3 docx2gcode.py "таблиця.docx" --preview centerline.svg --dry-run
python3 docx2gcode.py "таблиця.docx" --mode outline \
    --preview outline.svg --dry-run
```

## 5. Налаштування перед плотуванням

### Прев'ю в масштабі 1:1

Прев'ю створюється автоматично поруч із G-code — це SVG у справжніх
міліметрах разом із сіткою бланка. Роздрукуйте його **без масштабування
(100 %)** і накладіть на бланк — одразу видно, чи збігаються рядки й колонки.
`--preview file.svg` задає інший шлях, `--no-preview` вимикає створення.

### Пробна сітка

Щоб перевірити суміщення самим плотером, не витрачаючи час на текст:

```bash
python3 docx2gcode.py "таблиця.docx" \
    --grid calib -o calib.gcode
```

Плотер накреслить лише лінії таблиці. Накладіть результат на надрукований
бланк і за розбіжністю підберіть `--offset-x` / `--offset-y`.

`--grid full` малює і сітку, і текст — тоді бланк не потрібен зовсім,
пишемо на чистому аркуші.

### Підстроювання

| Симптом | Що змінити |
|---|---|
| текст зміщений праворуч/ліворуч | `--offset-x` (типово −6) |
| уся таблиця вище/нижче | `--offset-y` (типово −3; мінус = вгору) |
| колонка дати не там | `--date-offset-x` (типово −2; більше = праворуч) |
| колонка номерів не там | `--number-offset-x` (типово −5; мінус = ліворуч) |
| текст сидить високо/низько над лінією | `--baseline-offset` (+ вниз, − вгору) |
| літери надто щільні | `--letter-spacing 0.05` |
| нуль координат угорі зліва | `--origin top-left` |
| рядки поступово «утікають» угору | `--scale-y` (див. нижче) |
| збіг лише на непарних аркушах | `--even-offset-y` (див. нижче) |

### Вертикальна калібровка плотера

Окремий випадок, який не лікується зсувом. Симптом: **перший рядок збігається з
бланком, а далі текст поступово повзе вгору** — до середини аркуша набігає пів
рядка, у кінці цілий, і останній рядок бланка лишається порожнім. При цьому на
прев'ю все рівно.

Причина не в розкладці, а в самому плотері: по Y він проходить трохи менше, ніж
йому наказано, і помилка накопичується з відстанню. Лікується множником
`--scale-y` (типово 1.031), який навмисно розтягує вертикальні відстані, щоб
після «усушки» плотера вони збіглися з бланком.

Відлік ведеться від базової лінії **першого** рядка: саме там розбіжності
немає, тому перший рядок лишається на місці, а кожен наступний опускається
пропорційно віддаленню. Прев'ю показує розкладку **без** компенсації — тобто
те, що має вийти на папері після неї; порівнювати з бланком і далі потрібно
його. Реальний множник видно у звіті та в шапці `.gcode`.

Якщо після друку залишкове відхилення ще є, уточніть множник так:

```
новий = поточний + (недохід у мм) / (відстань між першим і останнім рядком у мм)
```

Для бланка `1 лист.docx` відстань між першим і останнім рядком — 155.8 мм.
Тобто зайвий недохід в один рядок (4.87 мм) — це +0.031 до множника. Знак
звичайний: текст усе ще втікає вгору — множник збільшити, почав з'їжджати вниз —
зменшити. Повністю вимкнути компенсацію: `--scale-y 1`.

### Парні аркуші

Якщо записи не влазять на один аркуш, скрипт робить `_p01`, `_p02`… — по файлу
на аркуш. Розкладка на них однакова, але **надрукований бланк парних аркушів
лежить на папері вище**, ніж непарних, тому запис на них теж треба підняти.

Це робить `--even-offset-y` (типово −7 мм, мінус = вгору): величина додається до
`--offset-y` на кожному парному аркуші (2-му, 4-му…), непарні лишаються як є.
Піднімається аркуш цілком — текст, сітка бланка і прив'язка вертикальної
калібровки, — тому взаємне положення тексту й ліній не змінюється.

Типові −7 мм підібрані по факту друку.
Якщо на пробному аркуші текст усе ще
не сідає на лінії, зміряйте, наскільки бланк другого аркуша вище за бланк
першого, — ця різниця і є значення. Якщо ваш друк однаковий на всіх аркушах —
`--even-offset-y 0`. Фактичний зсув видно у звіті та в шапці кожного `.gcode`
(рядок `offset`).

```bash
# бланк парного аркуша вище на 12 мм
python3 docx2gcode.py "таблиця.docx" --even-offset-y -12
```

## 6. Параметри

Значення за замовчуванням уже відповідають вашій специфікації —
без жодного прапорця буде саме те, що ви задали.

### Плотер

| Параметр | Типово | |
|---|---|---|
| `--feed` | 800 | робоча подача, мм/хв |
| `--z-safe` | 1.0 | висота підйому пера, мм |
| `--z-draw` | −1.5 | сила натиску, мм (відʼємне = нижче паперу) |
| `--feed-travel` | 3000 | швидкість холостих ходів, мм/хв |
| `--feed-z` | 2000 | подача по Z, мм/хв |

`--z-draw` мусить бути помітно менше за `--z-safe`, інакше перо не торкнеться
аркуша. Глибше (більш відʼємне) значення = сильніший натиск.

Типові −1.5 — це запас на нерівність поверхні: перо гарантовано пише і в
найнижчій точці аркуша. Платою є боковий відгин кінчика, тому подача знижена
до 800 мм/хв — на 1500 мм/хв перо не встигає за траєкторією і текст
перекошується. Якщо ваша поверхня рівна, ставте `--z-draw -0.4 --feed 1500`:
буде вдвічі швидше.

Перо піднімається й опускається на кожен контур, а контурів тут тисячі, тому
хід по Z займає більше часу, ніж саме письмо (41.6 м проти 21.0 м на два
аркуші). Через це `--feed-z` впливає на загальний час сильніше за `--feed`,
а `--z-safe` варто тримати мінімальним — 1 мм достатньо, щоб не чіркати.

## 7. Як влаштована розкладка

Геометрія береться **з бланка** `1 лист.docx`, а не задається в коді:

* сторінка 297 × 210 мм, поля 15 мм ліворуч, 17.5 мм зверху;
* таблиця зсунута на −5.1 мм (`tblInd`), колонки 15.0 / 22.5 / 216.3 / 22.4 мм;
* 35 рядків: 2 пропускаються + **33 рядки для запису**, висота рядка 4.87 мм
  (Times New Roman 12 pt з одинарним інтервалом).

Скільки перших рядків пропустити перед письмом, задає `--header-rows` (типово
2): перший рядок — заголовок, другий у бланку вже заповнений, тому запис
починається з третього рядка, на 32.12 мм від верху сторінки.

Автовизначення «шапка — це рядки з текстом» тут не використовується, бо воно
залежить від того, що саме вже вписано в бланк. Повернути його можна через
`--header-rows -1`, а писати з другого рядка — через `--header-rows 1`.

Далі:

1. Текст третьої колонки переноситься по словах під ширину колонки і
   вирівнюється по ширині (як в оригіналі). Посилання на документ-джерело —
   `(розділ …`, `(бойове розпорядження …`, `(позатермінове …`, `(клопотання …`,
   `(розпорядження …`, `(БД …` — завжди починається з нового рядка, у будь-якому
   регістрі. Рядок перед таким розривом по ширині не розтягується. Підпис
   «Командир N омбр підполковник Прізвище» розкладається так: «Командир N омбр»
   ліворуч, прізвище — на тому ж рядку праворуч, «підполковник» — рядком нижче,
   далі один порожній рядок.
2. Дата й час завжди займають два рядки в другій колонці — навіть якщо в
   джерелі їх набрали в одному абзаці («15.07.2026 08:30»). Діапазон часу
   («04:36-04:38») лишається цілим. Номер займає один рядок у першій колонці.
3. Запис, що не вміщається, продовжується на наступному аркуші
   (`--no-split` забороняє розрив).
4. Координати переводяться в систему плотера: `Y = 210 − Y_сторінки`.

Порядок письма — **рядок за рядком, зліва направо**: номер, потім дата, потім
текст того самого рядка, і лише тоді перо переходить на рядок нижче.
Оптимізація холостих ходів цього порядку не змінює: вона переставляє контури
тільки в межах одного рядка.

Розмір шрифта береться з самого джерела (12 pt) — його не треба
вказувати вручну.

## 8. Формат G-code

```gcode
; sheet 1 of 2
; font: Segoe Script 12pt mode=centerline
G21              ; міліметри
G90              ; абсолютні координати
G17
G0 Z1.2          ; перо вгору
G0 X11.096 Y173.895
G1 Z-0.4 F1000   ; перо вниз
G1 F2000
G1 X11.321 Y174.038
...
G0 Z1.2
M2
```

Коментарі — тільки ASCII і короткими рядками: буфер рядка GRBL — 80 байтів,
а частина відправників не приймає не-ASCII байти навіть після `;`.
`--no-comments` прибирає їх зовсім.

## 9. Типові команди

```bash
# перевірити шрифт
python3 docx2gcode.py "таблиця.docx" --check-font

# пробна сітка для суміщення
python3 docx2gcode.py "таблиця.docx" --grid calib -o calib.gcode

# бойовий запуск (G-code і прев'ю в gcodeOutput поруч із текою проєкту)
python3 docx2gcode.py "таблиця.docx" -v

# продовжити журнал із номера 16
python3 docx2gcode.py "таблиця-2.docx" --start-number 16

# посунути весь текст на 1 мм праворуч від типового
python3 docx2gcode.py "таблиця.docx" --offset-x -5

# скласти файли в інше місце
python3 docx2gcode.py "таблиця.docx" -o ~/Desktop/журнал
```
